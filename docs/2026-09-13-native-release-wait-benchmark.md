# 最终等待段的 C 候选测量

当前 ctypes 接法没有展示更低的 Python 返回延迟，暂不接入生产节拍器。本轮保留了可复查的 C 行为测试、微基准与失败记录，原 `JointRate`、100ms、1ms 物理步长、4tick 和无追赶规则均未修改。

## 真实行为检查

Linux C 库已编译。主会话补齐时间转换的最后一个可表示部分秒，拒绝非法 timespec 和真正的 int64 溢出。启用 UBSan 且遇错立即失败的 C 夹具通过 16 项检查：空指针/负参数、已过期/恰好到期、等值时钟、恰好 1ms/超出 1ns、初次和等待中时钟错误、回退、非法秒/纳秒、INT64_MAX 和两个溢出边界。Python 适配器 14 项纯测试通过；纯测试本身不证明 C 行为或性能。

首次微基准在导入阶段失败：同目录的 `native_release_wait.so` 抢在 `.py` 前被当成 CPython 扩展。它没有产生任何计时样本。第二次使用同一动态库的逐字副本 `libwksim_release_wait.so`，并更新默认编译输出名；旧失败未覆盖，没有重编或替换库来改变结果。

## 计时结果

三种模式轮转执行，各丢弃 30 个热身、保留 1000 次独立 1ms 等待。主指标为返回 Python 后立刻读取的时间减 deadline；单看 C 内部时钟样本会遗漏调用返回和 Python 恢复的时间。

| 模式 | 返回延迟中位数 | P95 | P99 | 1000次累计延迟 |
| --- | ---: | ---: | ---: | ---: |
| 原 Python 轮询形态 | 148.5 ns | 517 ns | 112058 ns | 2.532098 ms |
| ctypes.CDLL | 2979 ns | 16308 ns | 56062 ns | 6.517725 ms |
| ctypes.PyDLL | 2424 ns | 13601 ns | 59260 ns | 5.822768 ms |

C 内部采样迟到中位数均为 7 ns，Python 轮询为 26 ns；较早的内部时间不能代替完整返回延迟。各模式尾部分布有差异，但该单进程短基准未包含飞控、真实组工作、健康检查、睡眠、异步写入和完整窗口。没有调整 CPU 亲和性、优先级或 GC，轮转也不证明外部噪声对称。不能据此宣称 OS 原因、全场倍率改善或 RateUnmet 已修复。

生产代码本就通过 `self.now()` 实例属性读钟；独立审查中“本基准因此抬高生产基线”的表述不采用。下一候选应先验证直接 CPython 调用能否减少总返回开销，再核对正式接线和证据绑定。
